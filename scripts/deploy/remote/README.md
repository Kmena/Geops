# GEOPS Staging: SSH control package

This package is **prepared only**. It is not installed and does not authorize a deployment.

## Privilege boundary

`release.mjs` accepts caller-chosen plan, env, log and state paths; `preflight.mjs` and `migrate.mjs` also read caller-chosen files. `migrate.mjs` accepts a recorded authorization string but does not verify a signed approval. `create-plan.mjs` is an unprivileged manifest builder. None of these scripts is run as root by the wrapper. The privileged operations are limited to local Docker inspection, pull, a fixed SQL read, image verification and Compose `up` for `geops-api`/`geops-web` only. No migration, gate write, database restart, shell or arbitrary Docker argument is exposed.

The root-owned bundle contains the exact Compose, Nginx and entrypoint blobs from `052f4bec0633f829869699e9485a0fdc61bc1964`. The wrapper checks their SHA-256 values before every operation. It uses a sanitized environment, the local Docker socket, `--no-deps --no-build --pull never` for service changes, a root-only lock and audit log, 90-second readiness limits and one-time Ed25519 approvals. A signed release fixes commit, API/Web digests, `gps-base`, 21 SQL checksums, environment and policy hash. Separate deploy and rollback approvals explicitly fix action, environment, release commit and digests, release hash, source IDs, target IDs and a 30-minute maximum validity. Application rollback never changes PostgreSQL or the external gate.

## One-time operator installation

1. Review this branch and the installer; generate the deterministic archive with `python -B scripts/deploy/remote/package.py geops-control.tar.gz`. Compare its printed SHA-256 with the reviewed value through a trusted channel. Verify the installer file hash separately before running it as root.
2. Provision `/etc/geops-deploy` and `/etc/geops-deploy/secrets` as `root:root`, mode `0700`. Each of the six files named in `geops_deploy.py` must be `root:24001`, mode `0640`, and match the secret currently mounted in the active API. `abi` belongs to group `24001`, so both parent directories must remain root-only. The installer compares hashes without printing values. **Do not point the root bundle to `/opt/geops-staging`**: that checkout and its secret directory are owned by `abi`.
3. Provide an operator-controlled Ed25519 **public** key in a root-protected path. The private key stays off Staging. If GHCR later requires credentials, provision read-only Docker auth under `/etc/geops-deploy/docker` as root; no token belongs in the inbox, arguments or logs.
4. After review and explicit installation approval, the operator copies the reviewed installer to `/root/geops-deploy-install.py` with owner root and mode `0500`, hashes that protected copy, and compares it to the separately reviewed installer SHA-256. Then run `sudo python3 -I /root/geops-deploy-install.py PACKAGE.tar.gz REVIEWED_PACKAGE_SHA256 /root/geops-deploy-approval.pub`. The installer refuses to run from an `abi`-writable path. It checks the archive, the local Docker context, root ownership of host tools, A image IDs/health, secret hashes, policy/bundle checksums and `visudo`, then tests `status` and `verify` before installing sudoers. It does not restart services. A current valid backup is required by `verify` (maximum age 24 hours). If a late check fails, the operator may rerun the same installer after fixing the cause: it verifies every existing protected file against the same reviewed archive and preserves the audit log. It never overwrites a different file or an installed sudoers rule.

The sudoers rule permits `abi` to run only `/usr/local/sbin/geops-deploy` without a password. The wrapper accepts `status`, `preflight RELEASE_ID`, `prepare RELEASE_ID`, `deploy RELEASE_ID APPROVAL_ID`, `rollback APPROVAL_ID` and `verify`. The Windows client uses the fixed `geops-staging` SSH alias: `node scripts/deploy/remote/client.mjs status`.

The authorized signer uses `sign.mjs` with a private key on a trusted machine to create release and action approval files. Signing an action requires `--release-document` and `--release-sha`; the signer checks that the document bytes match the SHA and copies its commit/digests into the approval. The signer must review the exact JSON, SHA, digests, source and target IDs; the wrapper verifies the signature and consumes an action approval once. `client.mjs stage-release ID JSON SIG` and `stage-approval ID JSON SIG` upload signed **data** to an untrusted inbox. `prepare` may pull verified digests; `deploy` and `rollback` require separate signed action approvals. The policy pins 21 SQL migrations and `gps-base`; a schema or variant change requires a reviewed policy/bundle upgrade.

## Remaining operational validation

Local tests use a simulated Docker runner and real ephemeral Ed25519 signatures. They do not establish Staging rollback time, GPS continuity or sudoers behavior after installation. Before the first approved switch, confirm fresh backup, unchanged A IDs, gate epoch, 21/21 ledger, Nginx/Caddy routes, prepared B digests and the signed approval. Measure real deploy/readiness, GPS retries and B→A rollback in the supervised window. Keep A images and all volumes.

The SSH client waits longer than the wrapper's bounded activation/recovery attempts. An unexpected network disconnect or host failure can still interrupt the remote process after an image change; inspect the protected audit log, current container IDs and root-owned state before retrying. The installer may leave protected files if a late read-only check fails, but it installs sudoers last and a repeat invocation checks the partial tree before resuming. Linux lock behavior and partial-install recovery are tested in a private local Linux tree; the installed sudoers rule and real Compose A→B→A remain operational gates.
