## Brechas y compatibilidad

El PRD y SPEC-00 describen `device_assignment`, `route`, `visit_obligation` y outbox como propuestas (`specs/spec-00-technical-feasibility/data-model.md:14-23`; ADR-010), pero esos objetos no están en las migraciones auditadas. No se encontró worker de visitas ni catálogo de clientes. El `customer_id` de `mdm_binding` representa tenant de MDM, no cliente comercial. Hay un conflicto de alcance entre el tenant operativo literal `synthetic` de 0015 y una futura operación real; debe resolverse en el frente de identidad correspondiente, sin modificarlo aquí.

**Conclusión condicionada:** un primer motor backend es viable con `position_event` y `captured_at`, una vez existan agente y vínculo histórico con dispositivo, así como rutas autorizadas para leer evidencia. El módulo no requiere nuevos campos GPS en Android. Si las posiciones de una operación APK-first sin MDM no ingresan por la ruta actual, eso es un bloqueo de ingestión de otro frente, no justificación para alterar GPS v2 en este SDD. La llegada tardía posterior al plazo admitido por ingestión o a la purga no puede reevaluarse a partir de datos crudos: debe quedar `UNVERIFIABLE` o pendiente de decisión de retención.
