# Specify — requisitos de SPEC-02

**Enmienda vigente 2026-10-21:** [ADR-020 / DEC-GPS-OFFLINE-001](../architecture/adr/ADR-020-ultima-politica-valida-offline.md) sustituye exclusivamente el límite offline de ADR-017. La APK debe poder evaluar e iniciar jornadas posteriores con la última política válida sin Internet, dentro de `valid_from/valid_until` y horario conocido, cuando Android permita arrancar el FGS. El contrato HTTP v1 y el código aún no lo implementan; las notas de cortes anteriores de este archivo son históricas donde contradigan esta enmienda.

**P0 vigente de diseño:** [GPS-UPLOAD-STARTED-BLOCKER](gps-upload-started-blocker-p0-2026-10-21.md) precede waves A–E. La compuerta global de STARTED en `BatchSync` es un defecto confirmado de progreso de subida; R12–R17 son requisitos nuevos, pendientes de implementación. No modifican la independencia de captura de ADR-020.

## Enmienda propuesta: empresa única y capacidades por usuario (2026-10-19)

La decisión de negocio fija una empresa inicial, con varios administradores y conjuntos independientes de capacidades. Se propone [ADR-019](../architecture/adr/ADR-019-empresa-unica-administracion-por-capacidades-propuesto.md): un principal obtiene `gps.user.manage` mediante ceremonia local supervisada; establece explícitamente el tenant `synthetic` y gestiona invitaciones, capacidades y acceso tenant por usuario. No se conceden permisos al crear una cuenta, ni se delega `gps.user.manage` mediante la API ordinaria. Cada operación exige su capacidad en backend; `gps.location.read` y acceso tenant siguen siendo requisitos independientes para leer posiciones. Las operaciones ordinarias dentro del tenant no requieren un segundo administrador. Recuperación crítica y transferencia conservan controles reforzados. Las notas anteriores sobre admin2 y doble control de concesiones ordinarias son históricas; no se modifican requisitos de MDM ni se autoriza GPS real.

**Estado:** propuesta para revisión. Fuentes: [PRD v1.1](../prd/GEOPS-PRD-v1.1.md) RF-03–RF-07, RF-14–RF-15, RN-05/RN-07 y CA-02–CA-05; [SPEC-00](../spec-00-technical-feasibility/requirements.md); [SPEC-01](../spec-01-foundation-wave-0a/spec.md); [ADR-002](../architecture/adr/ADR-002-gps-propio.md), [ADR-003](../architecture/adr/ADR-003-ingesta-gps.md), [ADR-008](../architecture/adr/ADR-008-buffer-offline.md) y [ADR-012](../architecture/adr/ADR-012-identidad-dispositivo.md).

## Invariantes y casos límite

- Ventanas son intervalos semiabiertos `[inicio, fin)` en zona IANA. `inicio < fin` termina el mismo día, `inicio > fin` cruza medianoche y `inicio = fin` se rechaza; el día ISO 1–7 es el día local de inicio. DST, recorte por vigencia e instancias UTC siguen [ADR-017](../architecture/adr/ADR-017-politicas-gps-temporales-offline.md). El dispositivo no extiende una ventana por tolerancia de reloj.
- Una excepción por fecha local prevalece sobre la regla semanal de esa fecha: `OFF` o ventana sustitutiva válida. Dos excepciones para la misma fecha se rechazan; se conserva su origen administrativo y motivo. La publicación previsualiza las ventanas UTC resultantes.
- Vigencia explícita `valid_from < valid_until`, en UTC; `active=false` recibido cancela captura. La última política válida se conserva y puede autorizar nuevas jornadas offline dentro de esa vigencia; no existe límite automático de 12 h ni de primera ventana. Reinicio sin red exige política íntegra, tiempo evaluable y arranque Android legal; los detalles de tiempo entre boots siguen abiertos. La revocación no recibida puede tardar varios días y exige aceptación de privacidad/seguridad antes del piloto.
- Una sola revisión efectiva por dispositivo e instante. No hay precedencia individual/grupo: cualquier solape se rechaza (409), incluso al cambiar membresía. `assignment_version` crece por dispositivo ante cambios futuros, desasignación o revocación. La última **asignación ya validada** debe poder cubrir sus jornadas posteriores offline cuando el contrato versionado pruebe su alcance; una asignación distinta nunca se inventa offline. Reinstalación/restauración exige identidad vigente de SPEC-01.
- Frecuencias son objetivos, no garantías Android. Límites de contrato W1-A: captura 30–300 s y sincronización 60–900 s; 60 s GPS es referencia del PRD. El piloto puede estrecharlos tras batería/privacidad. `WorkManager` no define cadencia GPS de 60 s.
- El umbral de alerta por silencio durante una ventana autorizada se configura de 300 a 7200 s (predeterminado de diseño 900 s). Fuera de ventana no se crea alerta de ausencia de heartbeat ordinario.
- El envío ordena posiciones pendientes por `captured_at,event_id`, pero el servidor tolera llegada fuera de orden por reintentos; no se cambia `event_id` ni la hora de captura.
- Cambio de política durante una sesión: cerrar la sesión anterior con `POLICY_REPLACED`; evaluar nueva ventana y, si procede, abrir otra con nueva versión y nuevo provisional. No reetiquetar muestras históricas. La sesión canónica la crea el backend según [ADR-016](../architecture/adr/ADR-016-identidad-sesiones-gps.md).
- Captura real exige permisos, notificación e indicadores Android visibles. No se promete inicio automático desde segundo plano. Si Android lo impide, registrar `MISSED_START`/error y pedir interacción visible; no simular sesión.
- Empleados y asignaciones históricas siguen el modelo de SPEC-00; política por ID lógico de dispositivo o grupo, jamás UDID/serial como autorización.

## Fuera de alcance

MDM propio, cambios de ManageEngine, impedir desinstalación o desactivar ubicación, aprovisionar sin reset, cobertura multimarca, producción, visitas/rutas e inferencia de inicio/fin desde huecos GPS. Estos cuatro temas MDM son bloqueos independientes; no frenan contratos, UI ni lógica sintética de esta SPEC.
